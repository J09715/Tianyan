# 天衍工作流

天衍工作流是持久化的纯 Kotlin DAG 定义，由 Harness 调度，Compose 特性层负责浏览、启动、展示执行时间线和处理人工审批。工作流本身不依赖 Android SDK，可独立验证和测试。

## 入口

- 工作区页面右上角的“工作流”入口。
- 项目卡片菜单中的“运行工作流”。
- 智枢输入 `/wf` 打开当前项目的工作流目录；输入 `/wf <workflow-id>` 打开指定工作流的运行确认与参数表单。
- 工作区构建失败或生成 APK 后，智枢输入区会显示类型化事件驱动的建议药丸；点击后携带构建错误或 APK 路径启动对应工作流。

## 虚拟屏操作与录制

- 工作流目录新增“虚拟屏操作模板”，复制后编辑；HOST_ACTION 的“虚拟屏”分组提供创建屏幕、打开应用、点击、双击、长按、滑动、追加/替换输入、按键、等待和关闭屏幕。
- 每个操作都有“操作后等待（毫秒）”，可将 900 调到 300 或 0；手势的 `duration_ms` 与操作后的 `wait_ms` 分开。坐标统一为 0–1000，不能填写截图像素。独立 DELAY 节点也可切换秒/毫秒。
- 所有参数支持 `${VAR}`；输入支持多行并保留前后空白。替换输入向控件发送全选/粘贴按键，空文本可清空；控件是否接受需核对页面。
- 聊天中可要求“使用手机操作模型打开应用完成任务，并录制为工作流 XXX”；HOST `virtual_screen_task` 的 `workflow_name` 参数会在模型报告完成且无失败步骤、无人工介入时保存操作链。录制必须从打开应用开始，防止新建屏幕重放时没有应用画面。录制保留固定步骤及操作后等待，不包含模型请求耗时；录制文本保存为 `TEXT_1` 等可修改的运行变量，存储在本地工作流中。
- 保存后在工作区 → 工作流中编辑并复用。步骤按成功端口串联，默认遇错中止；重放固定步骤不调用模型，也不会自动识别页面变化。运行前需确认应用入口、登录状态和页面布局一致，操作步骤已发出不等于业务结果成功。
- session 留空时，各次运行使用独立会话，同一次运行的步骤共用屏幕。悬浮窗暂停/停止覆盖整个工作流；人工介入后需要核对页面再重新运行。同屏步骤禁止并行。可在末尾添加“关闭虚拟屏”释放屏幕；未添加时保留画面供核对。
- 手机模型请求明确限制 `max_tokens=2048`。开启智能体日志后，`PhoneAgent` 标签记录请求预算、步骤、图片尺寸、耗时、token 用量及输入结果；输入内容只记字数，日志不记录 API Key 或完整模型回复。

## 可视化编辑器

- P4 新增“插件动作”节点：填写已装配插件 ID、节点扩展 ID 和字面 JSON 参数；执行前必须确认。默认示例 `tianyan.harness/text-result` 仅输出指定文字。节点遵守现有调度、日志和恢复审查，详见 [工作流插件契约](PLUGIN_HARNESS_EXTENSIONS.md#工作流)。

- 新建自定义工作流，或从内置工作流创建可编辑副本。
- 目录顶部“导入 JSON”接受完整工作流定义文本：粘贴后异步校验并预览名称、节点/连接数量与并发上限，点击“导入并编辑”进入未保存草稿。输入变化会清除旧预览，校验完成后才能确认。导入生成全新工作流 ID，保留节点 ID、连接和变量引用；移除内置标记、原时间戳及主动推荐/FileWatch/slash command 触发绑定，统一手动触发。保存及运行沿用编辑器现有操作。
- 导入仅接受 `WorkflowDefinition` JSON，拒绝运行快照、未知字段、未知节点类型和无效 DAG；配置值必须是字符串。文本上限 524288 个字符、JSON 嵌套最多 32 层、最多 256 个节点和 1024 条连接；结果 schema、扩图结果源及并发上限仍按定义校验。导入不执行节点或调用模型。
- 导入窗的“选择 JSON 文件”使用系统文件选择器，也可继续粘贴文本；文件在 IO 线程有界读取，要求有效 UTF-8（支持开头的 UTF-8 BOM），最多读取 2097155 字节，并继续应用字符数及定义校验。取消选择保留原文本，读取期间不能确认导入，读取失败时需重新选择或修改文本；重复选择相同内容不会卡在校验状态。
- 编辑器“工作流信息 → 导出 JSON”导出当前已应用的定义，包含已应用但未保存的修改；尚未点击“应用”的输入框草稿不属于定义。点击后冻结本次定义快照、异步校验与生成 JSON，预览通过后可“复制完整 JSON”。导出保留节点 ID、连接、字符串配置、默认变量、布局及明确并发上限，移除内置标记、原时间戳与自动触发绑定，不包含运行上下文/输出/日志/审批记录，也不会自动保存或运行。
- 导出 JSON 可直接回到目录导入为新的手动工作流。无效图及超出导入容量的定义拒绝导出；通常使用格式化 JSON，接近字符上限时使用紧凑 JSON，绝不截断完整内容。弹窗预览最多展示前 24000 个字符，复制始终包含完整文本。剪贴板保留定义中的节点配置和默认变量，复制前需核对自行写入的个人内容。
- 导出窗可“保存为 JSON 文件”：系统保存窗口选择目标，建议名称去除路径/控制字符并保留 `.json` 后缀。写入的是点击保存时冻结的完整 JSON，以严格 UTF-8 编码写入；文件流成功刷新并关闭后才显示保存成功。系统文件提供者的写入不保证事务性，写入失败、取消或进程终止可能留下不完整文件，应用不将其报告为成功，也不自动删除所选文件。界面被重建后若待保存快照丢失，拒绝写入并要求重新导出。
- 节点可拖拽并按网格吸附；节点与连线共享同一画布变换。
- 支持添加、删除、选择节点，编辑标题、说明、超时、失败策略与 JSON 字符串键值配置。多行提示词以 `\n` 保存；无效 JSON 无法应用，不会静默丢失内容。
- 自动排版采用最长路径分层与重心排序减少交叉；属于同一编辑历史，可撤销/重做。内置流程默认使用分层坐标。
- 从节点发起连线并选择目标节点，自动拒绝重复连接、自连接和成环连接。
- 连接可选择任意输出、成功或失败端口，并支持 `exitCode == 0`、`output contains 文本` 和正则条件；编辑器校验与调度器共用同一套匹配语义。
- 支持删除连接、60 步撤销/重做、未保存离开确认和 Room 持久化。
- 可添加智能体推理与子智能体委派节点；两者支持提示词变量、等待、超时和结构化取消。

## 调度语义

- 就绪节点并发执行；任一节点完成且执行结果检查点写入成功后，立即重新计算可执行后继，不再等待无关节点一起结束。汇合节点仍等待所有直接依赖终态，`${previous.output}` 仅包含实际激活的直接上游。
- 每个工作流定义携带 `maxParallelNodes`，默认 4，允许 1–8；编辑器“工作流信息 → 最大执行并发”可修改，修改参与撤销/重做、保存及历史快照。没有此字段的旧 JSON 定义/记录按 4 解码；非法值在保存/运行前拒绝，不静默截断。设为 1 可串行执行普通节点。
- 人工审批节点（HUMAN_APPROVAL）不占执行名额，审批仍按队列显示。其它节点从派发到结果检查点完成占用名额，自动重试及 ASK_USER 失败重试等待也沿用该名额；就绪但无名额的节点保持 PENDING，超时从实际派发后开始计算。完成一个节点即释放一个名额，不等待整批。
- 动态扩图不能修改并发上限，新增分支与原节点共享名额；恢复沿用原运行快照的上限。该限制作用于单次工作流的节点执行，不限制多个工作流合计并发、节点内部子任务或已启动的托管后台服务总数。
- 条件边只激活匹配分支；未选分支会传播为 `SKIPPED`，不会让汇合节点永久等待。
- 节点支持超时、一次自动重试、用户确认后重试以及取消。
- 超时返回失败（退出码 124），不会误报为用户取消；重试耗尽、拒绝重试或其它非 CONTINUE 失败立即中止运行，并取消其它正在执行/等待确认的节点。已发生副作用不回滚；执行前日志未结算的外部动作，恢复时仍需核验并授权重试。
- 同一运行的并行审批按到达顺序展示，后到请求不覆盖当前请求；完成/取消当前请求立即展示下一项。请求身份隔离执行 ID 与节点 ID，旧请求的完成或取消清理不能删除新请求。多个运行的审批队列互相隔离。
- 已确认的扩图分支可以在其它分支等待审批时继续执行。执行进度快照中的成功状态不等于持久化完成，依赖派发只使用经过写入屏障的完成事件。
- 并行分支的全局变量写入顺序取决于完成顺序，不应同时写同名变量；需要确定输入时，显式连接依赖并引用对应节点的结构化结果。
- 定义保存前执行结构校验，包括重复 ID、悬空边、非法超时和环检测。
- 每次运行的完整状态历史写入 Room；数据库版本为 47。
- 编辑定义、重新播种内置流程不会删除历史；历史携带当时的定义快照，保存旧运行不会覆盖新编辑。目录底部可打开最近 5 次记录回看，也可一键「重跑」（沿用当时的定义、变量与工作区，显式用户动作才发起）。

## 手机与宽屏运行界面

- 手机时间线展示状态、实时耗时、运行进度、退出码、错误和产物路径。
- 运行时若已授予「显示在其他应用上层」，会显示工作流悬浮窗：当前节点/步骤、成功或失败、以及停止按钮。感知与点击等屏幕操作前会暂时卸下悬浮窗，避免 uiautomator 读到 HUD 节点；模型思考与节点等待时再显示。
- 日志 / Diff 可展开、滚动和选择复制；命令执行每约 300 ms 刷新日志尾部，保留最多约 200 万字符的流式缓存。
- 宽屏显示画布及右侧详情栏，点选节点查看同样的日志与结果；节点和连线仍使用统一世界坐标变换。
- 运行前统一显示确认表单：必填变量、可选默认变量；若流程含智能体节点，可从已配置模型列表中选择本次使用的模型（写入 `WORKFLOW_MODEL_ID` / `WORKFLOW_MODEL_VARIANT`，不改全局默认）。人工审批展示上游结果供审阅。

## 结构化智能体结果与增量检查点

智能体推理、子智能体委派节点可在配置 JSON 中设置 `resultSchema`（值是 JSON schema 的字符串）。未配置时保持原来的文本结果。配置后，会在任务提示词末尾追加结果契约，执行器对最终答复做严格本地校验；不是 Provider 原生 structured output，也不会为了修正格式自动追加模型调用。校验失败保留原始输出供查看，节点以退出码 2 失败，不向下游提供结构化值。智能体执行失败时同样不发布结构化值。

例如节点 `audit` 的配置：

```json
{
  "prompt": "检查当前项目，给出是否可以继续以及风险等级。",
  "resultSchema": "{\"type\":\"object\",\"required\":[\"approved\",\"severity\"],\"properties\":{\"approved\":{\"type\":\"boolean\"},\"severity\":{\"type\":\"string\",\"enum\":[\"low\",\"high\"]}},\"additionalProperties\":false}"
}
```

- 支持 `type`（object/array/string/boolean/integer/number/null）、`description`、`enum`、`properties`、`required`、布尔 `additionalProperties` 和 `items`；不支持的约束在保存/启动校验时明确拒绝，不静默忽略。顶层必须是对象，字段名使用字母/下划线开头、字母数字/下划线/连字符组成；schema 上限 32 KiB、答复上限 64 KiB、schema 校验递归深度上限 16。
- 后续提示词、命令、宿主参数和变量可引用 `${audit.result.approved}`、`${audit.result.severity}`；数组使用数字下标，如 `${audit.result.findings.0.path}`。对象/数组引用输出 JSON，缺失字段和 null 输出空串。
- `CONDITION_BRANCH` 的表达式可写 `${audit.result.approved} == true`，再用该条件节点的 `exitCode == 0` / `!= 0` 边分流。边表达式仍沿用现有出口条件语法，不直接解释结果字段。
- `${previous.result...}` 在普通插值中仅适用于唯一激活的直接前驱；多前驱应显式指定节点 ID。条件节点使用其求值的上游输出。
- 已完成节点立即合入运行状态的上下文，不必等待同批并行节点全部结束。历史观察器看到结果变化时绕过 3 秒日志节流保存快照；失败/取消和启动对账保留已保存的结构化结果及产物路径，旧历史 JSON 兼容读取。

检查点为 Room 运行快照；第二阶段在快照中保存有序执行日志并提供受控继续执行，具体边界见下节。产物路径沿用执行器已返回的列表，只保存引用，不复制文件，也不保证文件随后没有被移动或删除。

## 中断后继续执行

- 新运行携带 `journalVersion=1`。节点每次尝试在执行前保存 `STARTED`，结束后保存带结果的 `SETTLED`；两次写入都是等待完成的持久化屏障。执行前保存失败不派发动作，结果保存失败不派发依赖它的后继。并行节点的记录序号由互斥锁串行分配，历史写入拒绝较旧的日志序号/恢复次数覆盖较新快照。日志保存在现有 Room 快照 JSON 内，不新增表；每运行最多 10000 条记录，不做静默截断。
- 历史列表对可恢复的 FAILED/CANCELLED 运行显示“继续”。确认窗列出剩余步骤和需要重试的节点；用户先核对工作区/应用状态和产物，再逐个开启失败或结果不确定节点的重试。服务器侧重新读取历史，校验日志、定义、原发行版、恢复次数和日志长度；运行中、重复点击、过期确认、遗漏/额外重试节点均拒绝。
- 继续沿用原执行 ID 和历史定义，`resumeCount` 加一，保留执行日志；复用已保存的成功结果及 CONTINUE 策略下的失败结果，只执行其余节点，跳过分支重新按已保存结果计算。不能通过恢复 API 修改定义、模型输入或选择重跑成功节点。
- 日志中只有 STARTED、没有 SETTLED 的外部动作可能已发生，必须人工核验并授权重试；授权后追加 INTERRUPTED 记录，下一次尝试使用新序号。等待中的人工审批、延时和纯条件/变量节点可以重新进入；待审批重新请求，已完成审批结果沿用，恢复确认明确展示这个授权范围。
- 旧记录缺少执行前日志，仍只能“重跑”。含托管进程或虚拟屏/GUI 智能体的流程需要重建外部资源，本阶段不支持继续。当前发行版必须与原运行一致；不自动校验工作区文件内容、重新确认模型结论或保证产物文件仍存在。

进程死亡仍先对账为 CANCELLED，不自动续跑；用户必须显式点击继续。这里不承诺外部副作用 exactly-once：动作成功与结果落盘之间仍可能崩溃，恢复时以“结果不确定”处理。日志是快照中的有序记录，不是独立的 append-only 存储表；脚本热修补和跨定义缓存匹配尚未实现。

## 运行中追加流程

人工审批节点可配置 `expansionResultNode`，指定通过无条件 success 边直接连接的智能体结果源。结果源必须配置 `resultSchema`，成功返回顶层 `{ "nodes": [...], "edges": [...] }` 对象。编辑器提供结果 schema 与扩图结果源输入框；[完整配置示例](examples/dynamic-workflow.json) 展示“规划 → 确认 → 动态生成一个打印步骤”。复制完整 JSON → 工作流目录“导入 JSON” → 校验并编辑 → 保存 → 运行时选择自己的模型；示例没有实际调用过模型。

- 提案使用现有 `WorkflowNode` / `WorkflowEdge` JSON 格式，严格拒绝未知字段。每次允许 1–32 个节点、1–128 条边，序列化提案最多 65536 字符；扩图后最多 256 个节点、1024 条边。
- 新节点 ID 必须以审批节点 ID 加点号开头，后缀只能是 1–64 个字母、数字、下划线或连字符。不能复用已有节点/边 ID，不能添加指向已有节点的连线；入口边必须来自审批节点的 success 端口，所有新增节点必须可达且保持 DAG。保留原有节点、边和定义元数据。
- 追加独立后续分支；原图中审批节点的后继与新分支可并行，原后继不等待新分支完成，整个运行等待所有分支结束。需要汇合或串行的新增步骤应放在提案内部；不支持改写既有后继依赖、新增触发器、托管进程或宿主动作。
- 校验通过才请求确认；页面展示工作区与完整提案（包含命令、提示词、超时、失败策略和连接），勾选核对配置后可批准。后台通知的“查看提案”打开运行页，通知批准接口无法跳过提案审阅。确认仅覆盖新增步骤；变量引用在各步骤执行时解析，智能体自身工具调用仍按既有 Harness 权限与审批策略处理。规划节点本身按既有配置执行，不因输出提案而自动变成只读。
- 扩图审批成功的 SETTLED 记录同时保存提案、展开后的定义、原始定义和新增节点状态；写入成功之后才调度新节点。日志写入失败停止派发；拒绝/非法提案不添加节点。多个审批节点并发提出分支时，持久化互斥锁串行追加并再次校验。
- 中断恢复从原始定义按日志顺序重放已确认扩图，复核结果源提案、审批结果与最终定义；新节点不能在确认前有执行记录。沿用已确认图和已完成结果，未确认提案重新审批，不重新扩图或重跑成功的规划节点。历史“重跑”使用扩图前的原始定义，重新规划、重新确认。

此接口要求运行管理器提供持久化检查点；直接使用无检查点的调度器会拒绝扩图。

### 分阶段再规划

新增分支可以包含下一阶段的智能体与扩图审批节点，例如“确认第一批 → 执行诊断 → 根据 `${previous.output}` 规划下一批 → 再确认 → 执行”。新审批的 `expansionResultNode` 必须指向**同一提案内**带 schema 的智能体，并用无条件 success 边直接连接；不能借用外部阶段的结果源绕过本阶段规划。

扩图最多四层：原始审批计第一层，新审批 ID 必须位于父审批命名空间下，深度按已有扩图审批 ID 的点号前缀计数，同层并行分支各自计算。第四层只允许追加普通步骤，提案内不能再创建扩图审批。单批及整图容量限制继续生效，不能循环改写已有节点。

确认窗展示当前层数和后续扩图审批数量；本次批准只覆盖本批具体配置，未来生成的提案使用独立请求令牌，逐批重新确认。拒绝后续阶段按节点失败策略处理，默认中止整个运行并取消其它活动节点，不回滚前面已执行的动作；未确认或格式无效的后续提案不添加新节点。中断恢复按日志重建所有已确认层，复用已成功的诊断和规划；等待中的后续审批重新请求，旧确认令牌不能用于新请求。

[两阶段完整示例](examples/staged-dynamic-workflow.json) 的首批提案包含打印诊断、规划与第二次审批；下一次模型根据诊断输出生成打印总结。示例仅做本地解析与 Mock 链路验证，未调用真实模型；规划提示词中的“不调用工具”仍是提示约束，权限以 Harness 策略为准。目录保存扩图前的原定义，运行历史保留展开图；“重跑”重新从第一阶段开始。

## 内置流程

- 发布构建 → 确认 → APK 安装。
- 构建完成事件 → 确认安装刚生成的 APK。
- 构建失败事件 → 环境 doctor / analyze。
- 输入构建错误 → 只读智能体诊断 → 确认修改 → 子智能体最小修复 → Diff → 确认重新构建。
- APK 解包与反编译 → 智能体只读审计 → 带证据的报告；不强制覆盖已有解包目录。
- Git Diff → 智能体提交建议 → 用户输入确认提交说明 → 本地提交；不推送。
- **宿主自动化实验室**：权限探测 → 打开设置 → 等待前台 → 屏幕感知 → 通知（无特权则 Toast 降级）。
- **广播 + 系统设置演示**：变量 → 自定义广播 → 读亮度 → 审批后写亮度。
- **智能体 GUI 试飞**：特权检查 → 人工确认 → 打开 QQ → 本地 `gui_pilot` 循环（感知 → 模型 JSON 决策 → 点击），默认进天衍群发试飞文案。

## 节点与安全边界

当前可执行节点覆盖触发器、终止节点、Bash、托管进程、智能体推理、子智能体委派、天衍构建、**宿主动作（应用/广播/设置/GUI/特权 shell）**、**条件求值**、延时、设置变量和人工审批。

### 宿主动作（HOST_ACTION）

编辑器按分类选择动作；标记「需特权」的项要求设置中已切换到 **Shizuku 或 Root** 且授权生效：

- **诊断**：权限状态、桥健康、设备快照、logcat
- **应用**：打开应用、强停、清数据、冻结/解冻、授权/撤销权限、等待前台
- **Intent**：发送广播、启动 Activity/Service（支持 extras：`key=value` / `key:int=1` / `flag:bool=true`）
- **系统**：settings get/put、飞行模式、Wi‑Fi、媒体音量
- **GUI**：感知屏幕；点击/双击/长按/滑动/滚动/按键/粘贴（`HostGuiToolkit`：有 Shizuku/Root 时自动开通无障碍手势服务，再降级 `cmd input` / `bin input`；中文走剪贴板粘贴）
- **交互**：Toast、震动、剪贴板、通知
- **高级**：特权 shell、`cmd` 服务调用；未知 action 可回退到自定义 `command`

广播与启动 Activity 默认先走应用 Context；失败或勾选强制 shell 时走 `am broadcast` / `am start`。

### 条件分支（CONDITION_BRANCH）

节点配置 `expression` 并真正求值（不再只是透传）：

- `exitCode == 0` / `!=`
- `output contains …` / `output matches …`
- `${VAR} == …` / `!=` / `contains` / `matches` / 数值比较
- `empty VAR` / `notEmpty VAR`
- `&&` / `||` 组合

成立时节点 `exitCode=0` 并写入 `CONDITION_RESULT=true`；不成立为 `exitCode=1`。边上仍可用 `exitCode` / success·failure 端口分流。

### 其它

- `DELAY`：等待秒数；`SET_VARIABLE`：多行 `KEY=value` 注入全局变量。
- 内置发布工作流在 APK 安装前要求确认；智能提交只在本地提交，不默认推送远端。
- 新增内置示例：`host_automation_lab`（打开设置 + 屏幕感知）、`host_broadcast_and_settings`（广播 + 设置）。

智能体节点通过每次运行、每个节点独立的持久化 Harness 会话与 Lane 执行，不切换智枢当前会话。`prompt` 支持 `${WORKSPACE_PATH}`、`${变量名}`、`${节点ID.output}` 与 `${previous.output}`；后者只合并实际激活的直接前驱，按连线顺序输出，不受无关并行节点影响。子智能体节点可配置 `role`，或同时配置 `department` 与 `agentQuery`，写权限范围由逗号分隔的 `writePaths` 声明。

主动推荐目前接入构建失败、APK 产出两类领域事件，仅推荐、不自动执行。Git 脏状态与 FileWatch 仍是扩展点，没有启用后台监听。

## 后台运行与定时计划（2026-09）

- **运行与 UI 解耦**：执行由进程级单例 `WorkflowRunManager`（harness）持有，运行页退出/销毁 ViewModel 不再取消工作流；引擎层支持多运行并发，页面通过 `viewRun(executionId)` 切换关注的运行。目录页对仍在推进的运行显示「后台运行中」横幅，可一键查看。
- **持久化**：启动写 RUNNING 行，普通日志按约 3 秒节流，节点执行前/结果记录等待写入完成，终态写最终快照；历史行记录 `triggerSource`（MANUAL/SCHEDULE）与 `scheduleId`。进程被杀后启动对账（`reconcileInterruptedRuns`）把非终态行标为 CANCELLED（"进程曾被系统终止"），节点状态与日志保留，可在目录页按上述边界手动继续或重跑。
- **前台保活**：有运行时 Application 联动拉起 `WorkflowForegroundService`（dataSync + WakeLock/WifiLock），逐运行展示进度通知；结束发终态通知后自动退出。Android 15+ dataSync 6h 硬超时后服务按 DETACH 退出前台，运行继续。
- **审批**：后台出现待审批节点时发 IMPORTANCE_HIGH 通知，可直接「批准/拒绝」（`WorkflowApprovalReceiver`），点正文深链打开运行页（`AppNavigationTarget.WorkflowRun`）。
- **定时计划**：`workflow_schedules` 表 + WorkManager（UniqueWork，tag=计划 id）。重复方式：每天 HH:mm（24h 周期 + initialDelay）、每 N 分钟（下限 15）、一次性延时（触发后自动停用）。WorkManager 按需初始化（`Configuration.Provider` + KoinWorkerFactory），进程被杀/设备重启后到点自动拉起执行。到点 Worker 走 `WorkflowRunManager.start(trigger=SCHEDULE)`；沙箱未就绪先等待（约 2 分钟），未安装 RootFS 不自动下载，直接落 FAILED 历史。DAILY/INTERVAL 在 Doze 下可能有分钟级顺延。
- **会话恢复边界**：`workflow:<executionId>:<nodeId>` 前缀的 Harness 会话不参与 `recoverAllInterruptedSessions` 自动续跑，避免死运行的副作用重放。修复流程拒绝后续审批不会自动回滚已有修改。

## 验证范围

扩图后的运行/历史画布使用展示副本按 DAG 依赖分层布局，同层分支错开，后续批次追加时重新计算展示位置并适配视口；审批提案、运行定义、日志、结果和恢复校验保留原坐标与内容。普通流程及可编辑画布沿用用户坐标。画布同步新增/删除节点与外部坐标变化（包括编辑器自动布局），只在来源坐标改变时覆盖本地位置，未变更的节点保留进行中的拖动位置；旧历史结构不合法时跳过展示布局。

运行页、编辑器运行详情和历史回看的节点详情，对含 `structuredResult` 的输出提供“查看结构化结果”。窗口固定打开时的 JSON 对象，后台线程生成完整 JSON 并按最多 6000 字符分页，不拆分 emoji 的 UTF-16 字符对，末尾内容可翻页查看。复制与系统文件保存使用完整结果，排版超过传输上限时退回完整紧凑 JSON，超过上限报错而不截断。保存的结果文件不是工作流定义，不能通过目录导入为可执行流程；无结构化结果的旧历史保持原有日志入口。

人工审批默认不限时等待，通用 `WorkflowNode.timeoutSeconds` 不控制审批等待。编辑器为审批节点提供独立的“审批等待上限”输入框：留空移除配置；填写时写入 `config.timeoutSeconds`，仅接受 1–3600 秒的整数。JSON 导入、导出、保存、扩图和执行前使用同一校验；空字符串、0、负数、非整数、变量引用及超限值不会退化为无限等待。普通执行节点的超时输入同样限定为 1–3600 秒，非法输入不能应用，不再静默钳制。

审批等待超时产生退出码 124，撤销该请求并按节点失败策略处理；过期请求不能继续批准。默认无限等待、精确超时边界和过期决策清理使用虚拟时钟与假执行器回归，不调用模型 API。

自动化覆盖 DAG 分支与并发、超时恢复、立即取消、重试耗尽、并行审批、直接上游传参、布局稳定性以及 Room 历史保留。设备上的 Linux 工具链、模型账号、安装权限仍是端到端运行的前置条件；编译或单元测试通过不等同于真实模型/构建/安装全链路验收。
